HTTPS(HyperText Transfer Protocol Secure)는 기존 HTTP 프로토콜의 보안적 약점(평문 전송으로 인한 도청, 데이터 변조, 신원 위장)을 해결하기 위해, HTTP 아래에 **SSL/TLS (Secure Sockets Layer / Transport Layer Security)** 암호화 계층을 추가한 프로토콜입니다.

## 1. 대칭키 암호화 vs 비대칭키(공개키) 암호화

HTTPS는 두 암호화 방식의 단점은 보완하고 장점만 결합한 **하이브리드 암호화 방식**을 사용합니다.

> **대칭키:** 암호화키와 복호화키가 같은 방식으로 암호화된 데이터를 전송할 때 복호화키도 같이 전송해야 함
> **비대칭키:** 공개키와 개인키로 구성된 방식
- **클라이언트 -> 서버:** 클라이언트는 서버의 공개키로 암호화를 수행하여 전송, 서버는 자신의 개인키를 사용하여 복호화 수행
### 1. 대칭키 vs 비대칭키 암호화 비교 표

|**구분**|**대칭키 암호화 (Symmetric Key)**|**비대칭키 암호화 (Asymmetric Key)**|
|---|---|---|
|**키 구조**|암호화 키 = 복호화 키 (1개의 키 사용)|공개키(Public Key) ≠ 개인키(Private Key) (2개의 키 사용)|
|**속도 및 연산 부하**|매우 빠름, 연산 부하 적음|상대적으로 매우 느림, 복잡한 수학적 연산 필요|
|**키 전달의 문제**|키를 상대에게 전달할 때 탈취 위험 존재|공개키는 공개되어도 안전하므로 키 전달이 손쉬움|
|**주요 알고리즘**|AES, DES, ARIA, ChaCha20|RSA, ECC, Diffie-Hellman|
|**HTTPS 내 역할**|실제 데이터를 주고받을 때 빠른 암복호화용|대칭키(Session Key)를 안전하게 교환하기 위한 수단|

### HTTPS의 하이브리드 전략

- **데이터 본문 전송:** 속도가 빠르고 효율적인 **대칭키**로 대용량 데이터를 암호화합니다.
    
- **대칭키 전달 과정:** 데이터를 암호화할 대칭키(이를 **세션 키, Session Key**라 부름)를 상대방에게 안전하게 보낼 때만 연산이 heavy한 **비대칭키(공개키)** 방식을 사용합니다.
    

## 2. CA(Certificate Authority) 인증서

서버가 제공하는 공개키가 "진짜 그 사이트의 공개키인가?"를 검증하기 위해 신뢰할 수 있는 제3자 기관인 CA(공인 인증 기관)가 발급하는 전자 문서입니다.

### CA 인증서의 구성 및 검증 원리

1. **서버의 공개키 + 서버 정보(도메인 등):** CA 기관에 전송합니다.
    
2. **CA의 전자 서명:** CA는 해당 정보를 CA 자체의 개인키로 암호화(서명)하여 인증서를 발급합니다.
    
3. **클라이언트(브라우저) 검증:**
    
    - OS나 브라우저에는 이미 세계적으로 신뢰받는 **Root CA들의 공개키**가 사전에 내장(Pre-installed)되어 있습니다.
        
    - 브라우저는 내장된 **CA 공개키로 인증서의 서명을 복호화**하여, 해당 서버가 신뢰할 수 있는 CA로부터 검증받았는지 확인합니다.
        

## 3. SSL/TLS Handshake 과정 (TLS 1.2 기준)

클라이언트와 서버가 암호화 통신을 시작하기 전, **서버 신원 검증 및 세션 키(대칭키)를 안전하게 나누어가지는 과정**입니다.
### 2. SSL/TLS Handshake 단계별 진행 표

|**단계**|**주체**|**동작 / 메시지 명칭**|**세부 내용**|
|---|---|---|---|
|**1**|Client $\rightarrow$ Server|**Client Hello**|지원하는 TLS 버전, 암호화 방식 목록(Cipher Suites), **Client Random(난수)** 전달|
|**2**|Server $\rightarrow$ Client|**Server Hello**|클라이언트 제안 중 선택된 암호화 방식, **Server Random(난수)** 전달|
|**3**|Server $\rightarrow$ Client|**Certificate**|서버의 **CA 인증서(서버 공개키 포함)** 전달|
|**-**|Client|_(인증서 검증 및 난수 생성)_|내장된 CA 공개키로 인증서 검증 후, 무작위 난수인 **Premaster Secret** 생성|
|**4**|Client $\rightarrow$ Server|**Client Key Exchange**|서버 공개키로 암호화한 **Premaster Secret** 전달|
|**-**|Client & Server|_(Session Key 계산)_|`Client Random` + `Server Random` + `Premaster Secret`을 조합해 동일한 **Session Key(대칭키)** 생성|
|**5**|Client $\rightarrow$ Server|**Finished (암호화)**|생성된 Session Key로 암호화한 테스트 메시지 전송 (Handshake 종료 준비)|
|**6**|Server $\rightarrow$ Client|**Finished (암호화)**|생성된 Session Key로 암호화한 테스트 메시지 응답 (Handshake 정상 종료)|
|**7**|Client $\leftrightarrow$ Server|**HTTPS 데이터 통신**|이후 모든 HTTP 요청/응답은 완성된 대칭키(**Session Key**)로 암복호화하여 진행|

### 단계별 세부 동작 흐름

1. **Client Hello:**
    
    - 클라이언트가 지원하는 TLS 버전, 암호화 알고리즘 목록(Cipher Suite), 그리고 클라이언트가 생성한 난수(**Client Random**)를 보냅니다.
        
2. **Server Hello & Certificate:**
    
    - 서버는 사용할 암호화 방식을 선택하고, 서버가 생성한 난수(**Server Random**)와 함께 자신의 CA 인증서(서버 공개키 포함)를 전달합니다.
        
3. **인증서 검증 및 Premaster Secret 생성:**
    
    - 클라이언트는 브라우저에 내장된 CA 공개키로 서버 인증서를 검증합니다.
        
    - 검증이 완료되면, 클라이언트는 세션 키의 원재료가 될 새로운 난수인 **Premaster Secret**을 생성합니다.
        
4. **Client Key Exchange:**
    
    - 클라이언트는 **서버의 공개키**로 `Premaster Secret`을 암호화하여 서버로 전송합니다.
        
    - (서버만 개인키를 가지고 있으므로, 중간에서 누군가 탈취해도 `Premaster Secret`을 복호화할 수 없습니다.)
        
5. **세션 키(Session Key) 조합:**
    
    - 클라이언트와 서버는 똑같이 공유하게 된 **Client Random + Server Random + Premaster Secret** 3가지 요소를 조합하여 동일한 대칭키(Session Key)를 만들어냅니다.
        
6. **Handshake 완료 (Finished):**
    
    - 양측은 준비가 완료되었음을 알리고, 이후 발생하는 모든 HTTP 데이터(요청/응답)는 이 Session Key(대칭키)를 이용해 암호화하여 주고받습니다.
