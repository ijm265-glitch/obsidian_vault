# 1. 3-Way Handshake (연결 설정 과정)
3-Way Handshake는 클라이언트와 서버가 **양방향 통신을 시작하기 전, 서로 연결 상태를 확인하고 패킷의 순서 번호(Sequence Number)를 동기화**하기 위한 3단계 과정입니다.

```
[ Client ]                                                       [ Server ]
CLOSED                                                           LISTEN
  │                                                                │
  ├───────────── 1. SYN (Seq = x) ───────────────────────────────> │ SYN_RCVD
  │                      [State: SYN_SENT]                         │
  │                                                                │
  │<──────────── 2. SYN-ACK (Seq = y, Ack = x + 1) ────────────────┤
  │                                                                │
  │ ──────────── 3. ACK (Seq = x + 1, Ack = y + 1) ──────────────> │ ESTABLISHED
                 [State: ESTABLISHED]                               
```

### Initial State (초기 상태)
- **Server:** 포트를 열고 클라이언트의 연결 요청을 대기하는 **`LISTEN`** 상태입니다.
- **Client:** 연결이 생성되지 않은 **`CLOSED`** 상태입니다.
### Step 1: SYN (Client ➔ Server)

> _"나 너랑 연결하고 싶어. 내 패킷 시작 번호(ISN)는 x야."_

- **Client 동작:**
    - 연결을 요청하기 위해 TCP 헤더의 **`SYN` 플래그를 1로 설정**한 세그먼트를 생성합니다.
    - 자신이 사용할 무작위 난수 기반의 초기 순서 번호(**`ISN: Initial Sequence Number = x`**)를 설정하여 서버로 전송합니다.
- **상태 변화:** Client: `CLOSED` ➔ **`SYN_SENT`**
### Step 2: SYN-ACK (Server ➔ Client)

> _"연결 수락할게! 내 시작 번호는 y이고, 네가 보낸 x 잘 받았으니 다음엔 x+1번을 보내줘."_

- **Server 동작:**
    - `SYN` 패킷을 받은 서버는 요청을 수락한다는 의미로 **`SYN` 플래그와 `ACK` 플래그를 모두 1로 설정**합니다.
    - 자신의 초기 순서 번호(**`Sequence Number = y`**)를 새로 생성합니다.
    - 클라이언트가 보낸 `x`를 잘 받았음을 증명하고 다음 바이트를 요구하기 위해 `Acknowledgment Number = x + 1`로 설정하여 전송합니다.
- **상태 변화:** Server: `LISTEN` ➔ **`SYN_RCVD`**
    
### Step 3: ACK (Client ➔ Server)

> _"확인했어! 네가 보낸 y도 잘 받았으니 다음엔 y+1번을 기대할게. 이제 데이터 주고받자!"_

- **Client 동작:**
    - 서버의 응답을 수신한 클라이언트는 **`ACK` 플래그를 1로 설정**한 세그먼트를 보냅니다.
    - 자신의 `Sequence Number`는 `x + 1`이 되며, 서버가 보낸 `y`를 확인했으므로 `Acknowledgment Number = y + 1`로 설정합니다.
    - _(참고: 이 3번째 ACK 세그먼트부터는 실제 애플리케이션 데이터(HTTP 요청 등)를 함께 실어서 보낼 수 있습니다.)_
        
- **상태 변화:**
    - Client: `SYN_SENT` ➔ **`ESTABLISHED`**
    - Server: `SYN_RCVD` ➔ **`ESTABLISHED`** (ACK 수신 직후)

# 2. 4-Way Handshake (연결 해제 과정)

데이터 전송이 모두 끝나면, 클라이언트와 서버 양쪽의 자원을 안전하게 반환하기 위해 **4단계에 걸쳐 연결을 해제**합니다. TCP는 양방향 통신이므로 **각 방향의 연결을 각각 종료**해야 합니다.
```
[ Active Closer (Client) ]                       [ Passive Closer (Server) ]
ESTABLISHED                                                      ESTABLISHED
  │                                                                   │
  ├────── 1. FIN (Seq = a) ─────────────────────────────────────────> │ CLOSE_WAIT
  │       [State: FIN_WAIT_1]                                         │
  │                                                                   │
  │ <──── 2. ACK (Ack = a + 1) ───────────────────────────────────────┤
  │       [State: FIN_WAIT_2]                                         │ 
  │        (남은 데이터 전송 중)                                        │
  │                                                                   │
  │ <──── 3. FIN (Seq = b) ───────────────────────────────────────────┤ LAST_ACK
  │                                                                   │
  │ ────── 4. ACK (Ack = b + 1) ────────────────────────────────────> │ CLOSED
  │       [State: TIME_WAIT]                                          │
  │       (Timer 동작 후)                                              │
  ▼                                                                   │
CLOSED                                                                │
```

_(여기서는 먼저 종료를 요청한 쪽을 Client로 가정합니다.)_

### Step 1: FIN (Client ➔ Server)

> _"나는 더 이상 보낼 데이터가 없어. 내 쪽 연결을 끝낼게."_
- **Client 동작:**
    - 전송할 데이터가 더 이상 없음을 알리기 위해 **`FIN` 플래그를 1로 설정**하여 전송합니다.
- **상태 변화:** Client: `ESTABLISHED` ➔ **`FIN_WAIT_1`**
### Step 2: ACK (Server ➔ Client)

> _"네가 종료한다는 거 잘 확인했어(a+1). 하지만 난 아직 보낼 데이터가 남았을 수 있으니 정리하고 다시 연락할게."_

- **Server 동작:**
    - 클라이언트의 `FIN`을 수신하고, 이에 대한 확인으로 `ACK` 플래그(Ack = a + 1)를 응답합니다.
    - 이 순간 클라이언트 ➔ 서버 방향의 연결만 종료(Half-Close)되며, 서버는 남아있는 데이터나 처리 중인 작업을 계속 전송합니다.
- **상태 변화:**
    - Server: `ESTABLISHED` ➔ **`CLOSE_WAIT`**
    - Client: ACK 수신 후 `FIN_WAIT_1` ➔ **`FIN_WAIT_2`**
        

### Step 3: FIN (Server ➔ Client)

> _"나도 남은 데이터 처리가 모두 끝났어. 이제 내 쪽 연결도 끝낼게."_

- **Server 동작:**
    - 남은 데이터를 모두 보내고 정리 작업이 끝나면, 서버도 **`FIN` 플래그를 1로 설정**하여 클라이언트에 종료 요청을 보냅니다.
- **상태 변화:** Server: `CLOSE_WAIT` ➔ **`LAST_ACK`**
    

### Step 4: ACK (Client ➔ Server) 및 TIME_WAIT

> _"네 종료 요청도 잘 받았어(b+1). 수고했어!"_

- **Client 동작:**
    - 서버의 `FIN`을 받고, 이에 대한 최종 확인으로 `ACK` 플래그(Ack = b + 1)를 응답합니다.
    - 서버는 이 ACK를 받고 즉시 **`CLOSED`** 상태로 전환되어 자원을 반환합니다.
        
- **상태 변화:**
    - Server: `LAST_ACK` ➔ **`CLOSED`**
    - Client: `FIN_WAIT_2` ➔ **`TIME_WAIT`** ➔ (일정 시간 대기 후) **`CLOSED`**
        

### 💡 핵심 포인트: Client는 왜 바로 종료하지 않고 `TIME_WAIT`를 가질까?

`TIME_WAIT`는 보통 **2 MSL(Maximum Segment Lifetime, 약 1~2분)** 동안 유지되며, 두 가지 치명적인 문제를 방지하기 위해 존재합니다.

1. **마지막 ACK 손실 대비:**
    - Client가 보낸 마지막 4번째 `ACK` 패킷이 네트워크 지연으로 손실되면, Server는 계속 `LAST_ACK` 상태에 갇혀 `FIN`을 재전송하게 됩니다. Client가 `TIME_WAIT` 상태로 남아있어야 재전송된 `FIN`을 받고 다시 `ACK`를 보내 서버를 완전히 종료시킬 수 있습니다.
        
2. **지연 패킷(자투리 패킷) 혼선 방지:**
    - 이전 연결에서 네트워크에 떠돌던 지연 패킷(Delayed Segment)이 새로 열린 동일한 포트의 통신으로 잘못 흘러들어가는 데이터 오염을 막기 위해 기존 패킷이 완전히 소멸될 때까지 기다립니다.
