## 1. Client-Server 구조와 무상태성 (Stateless)

### 1) Client-Server 모델

- **요청(Request)과 응답(Response) 구조:** 클라이언트(웹 브라우저, 앱 등)가 서버에 요청을 보내면, 서버는 요청을 처리한 뒤 응답을 반환합니다.
    
- **역할의 분리:** 클라이언트는 UI/UX 및 사용자 입력을 담당하고, 서버는 비즈니스 로직 및 데이터 관리를 전담하여 시스템의 확장성과 독립성을 높입니다.
    

### 2) 무상태성 (Stateless)

- **상태 미유지:** 서버는 이전 요청의 상태나 클라이언트의 정보를 기억하지 않습니다. 모든 요청은 서로 완전히 **독립적**입니다.
    
- **장점 (확장성):** 서버가 클라이언트의 상태를 저장하지 않으므로, 서버를 무한히 늘리는 수평 확장(Scale-out)이 매우 용이하며 서버 응답성이 뛰어납니다.
    
- **단점 (보완 필요):** 로그인 상태 유지, 장바구니 정보 기억 등 이전 동작과의 연계가 필요한 상황에서는 추가적인 메커니즘(Cookie, Session, Token)이 필수적입니다.
    

## 2. HTTP 요청 메서드 (HTTP Request Methods)

클라이언트가 서버에게 "어떤 동작을 수행해 달라"고 요구하는 목적을 명시하는 방법입니다.

|**메서드**|**주요 역할**|**주요 특징**|
|---|---|---|
|**GET**|리소스 **조회**|URL 쿼리 파라미터로 데이터를 전달하며, 안전하고 멱등성(Idempotent)을 가짐|
|**POST**|리소스 **생성/등록**|요청 본문(Body)에 데이터를 실어 전송하며, 서버의 상태 변경을 유발함|
|**PUT**|리소스 **전체 수정**|대상 리소스가 있으면 완전 교체, 없으면 새로 생성함|
|**PATCH**|리소스 **부분 수정**|대상 리소스의 일부 필드만 변경함|
|**DELETE**|리소스 **삭제**|지정한 리소스를 제거함|

> **안전(Safe):** 호출해도 서버의 리소스를 변경하지 않음 (GET)
> 
> **멱등성(Idempotent):** 동일한 요청을 여러 번 보내도 결과가 항상 동일함 (GET, PUT, DELETE)

## 3. HTTP 상태 코드 (Status Codes)

서버가 클라이언트의 요청을 처리한 결과를 3자리 숫자로 응답합니다.

- **1xx (Informational):** 요청이 수신되어 처리 중임 (실무에서 직접 다룰 일은 적음)
    
- **2xx (Successful) - 성공:**
    
    - **200 OK:** 요청이 정상적으로 처리됨
        
    - **201 Created:** 요청이 성공하여 새로운 리소스가 생성됨 (POST 결과)
        
- **3xx (Redirection) - 리다이렉션:**
    
    - **301 Moved Permanently:** 요청한 리소스의 URI가 영구적으로 변경됨
        
    - **304 Not Modified:** 리소스가 수정되지 않았으므로 클라이언트의 캐시를 사용함
        
- **4xx (Client Error) - 클라이언트 오류:**
    
    - **400 Bad Request:** 잘못된 문법이나 데이터 전달로 인한 요청 오류
        
    - **401 Unauthorized:** 인증(Authentication) 필요 (로그인 필요)
        
    - **403 Forbidden:** 인가(Authorization) 실패 (권한 없음)
        
    - **404 Not Found:** 요청한 리소스를 서버에서 찾을 수 없음
        
- **5xx (Server Error) - 서버 오류:**
    
    - **500 Internal Server Error:** 서버 내부 로직 예외 및 오류 발생
        
    - **503 Service Unavailable:** 서버 과부하 또는 점검으로 일시적 이용 불가
        

## 4. HTTP 헤더, 쿠키(Cookie), 세션(Session)

Stateless 특성을 극복하고 데이터를 효율적으로 전달하기 위해 활용되는 핵심 요소들입니다.

### 1) HTTP 헤더 (Headers)

요청 및 응답에 대한 부가적인 제어 정보(메타데이터)를 담고 있습니다.

- **General Header:** 요청/응답 공통 정보 (예: `Date`)
    
- **Request Header:** 클라이언트 상태 및 요청 조건 (예: `User-Agent`, `Authorization`, `Accept-Language`)
    
- **Response Header:** 서버 응답 정보 (예: `Server`, `Set-Cookie`)
    
- **Entity / Representation Header:** 본문(Body) 데이터의 타입 및 크기 (예: `Content-Type: application/json`, `Content-Length`)
    

### 2) 쿠키 (Cookie)

- **개념:** 서버가 클라이언트(브라우저)에 저장시키는 작은 데이터 조각(Text)입니다.
    
- **동작:** 서버가 응답 헤더(`Set-Cookie`)로 넘겨주면, 브라우저는 해당 도메인에 요청을 보낼 때마다 요청 헤더(`Cookie`)에 자동으로 담아 전송합니다.
    
- **특징:** 클라이언트 측에 저장되므로 보안에 취약하며, 주로 쿠키 만료 시간(Expires/Max-Age)이나 식별용 ID 정도를 담습니다.
    

### 3) 세션 (Session)

- **개념:** 중요한 클라이언트 상태 정보를 **서버 메모리나 DB에 저장**하고 관리하는 방식입니다.
- 이때 서버가 **"아, 이 녀석 아까 로그인한 걔구나!"** 하고 알아차릴 수 있도록, 서버 내부 저장소(RAM, Redis, DB 등)에 올려놓는 **'사용자 상태 기록표(장부)'** 그 자체를 **세션**이라고 부릅니다.
    
- **동작:**
    
    1. 클라이언트가 로그인 요청을 보냅니다.
        
    2. 서버는 난수 형태의 고유한 **Session ID**를 생성하여 서버 메모리에 사용자 정보와 매핑해 저장합니다.
        
    3. 서버는 응답 헤더(`Set-Cookie`)로 `Session ID`만 쿠키에 담아 보냅니다.
        
    4. 클라이언트는 이후 요청마다 `Session ID` 쿠키를 보내어 자신이 인증되었음을 증명합니다.
## 쿠키와 세션의 활용
#### 1단계: 로그인 
1. 클라이언트가 서버에 아이디/비밀번호(POST)를 보냅니다.
    
2. 서버는 비밀번호가 맞는지 확인하고, 서버 메모리(세션)에 `Session ID: A123 = 홍길동` 이라고 장부에 기록합니다.
    
#### 2단계: 쿠키발급

1. 서버는 Response Header의 `Set-Cookie`라는 칸에 `Session ID = A123`을 적어서 클라이언트에게 응답을 보냅니다.
    
2. 브라우저는 이 `Session ID = A123`이라는 조각(쿠키)을 자기 하드디스크에 살짝 저장해 둡니다.
    
#### 3단계: 이후 페이지 이동 

1. 클라이언트가 다른 페이지(예: 마이페이지)로 이동할 때, 브라우저는 요청 Header의 **`Cookie`** 칸에 저장해둔 `Session ID = A123`을 **자동으로 담아서** 서버로 보냅니다.
    
2. 서버는 요청 헤더에 있는 `Session ID = A123`을 보고, 자기 장부(세션)를 조회합니다.
    
    - _"아! A123번은 아까 로그인한 홍길동이구나!"_ 하고 매번 로그인시킬 필요 없이 홍길동의 마이페이지를 보여줍니다.


- **특징:** 민감한 정보는 서버에만 존재하므로 쿠키 방식보다 보안성이 높지만, 서버 메모리 사용량 증가 및 Scale-out 시 세션 정합성(Session Sync, Redis 등 필요) 문제를 고려해야 합니다.
