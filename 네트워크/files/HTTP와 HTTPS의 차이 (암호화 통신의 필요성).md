HTTP와 HTTPS의 가장 핵심적인 차이는 보안성(암호화)에 있습니다.

- **HTTP (HyperText Transfer Protocol):** 데이터를 **암호화하지 않은 쌩 텍스트(Plain Text)** 상태로 주고받는 통신 규약입니다.
    
- **HTTPS (HTTP Secure):** HTTP에 SSL/TLS(Transport Layer Security)라는 암호화 프로토콜을 얹어, 데이터를 주고받는 통로 자체를 암호화한 통신 규약입니다.
    

### 1. 왜 암호화 통신(HTTPS)이 필요한가?

HTTP로 네트워크 통신을 진행할 경우, 클라이언트와 서버 사이의 통신망 중간에서 누구든 packet을 엿보거나 변조할 수 있습니다. 이를 막기 위해 HTTPS가 도입되었습니다.

HTTPS는 다음 **3가지 핵심 위협**을 방지합니다.

#### ① 도청(Eavesdropping) 방지 — 데이터 패킷 암호화

HTTP 통신에서는 아이디, 비밀번호, 카드 번호, OAuth 토큰 등이 평문으로 전송됩니다. 같은 Wi-Fi 망이나 중간 공유기, ISP 단에서 패킷 스니핑(Packet Sniffing)을 할 경우 민감 정보가 그대로 노출됩니다.

HTTPS는 데이터를 암호화하여 통로를 통과시키므로, 중간에서 패킷을 빼내더라도 해독 불가능한 난수 형태로 보이게 됩니다.

#### ② 위·변조(Data Tampering) 방지 — 데이터 무결성 보장

중간자 공격(MitM, Man-in-the-Middle)을 통해 전달되는 데이터를 도중에 바꾸는 공격을 방지합니다. HTTPS는 데이터가 송신될 때의 내용과 수신될 때의 내용이 동일한지 기억 장치(MAC, Message Authentication Code 및 디지탈 서명)를 통해 무결성을 검증합니다.

#### ③ 위장(Spoofing) 방지 — 서버 신원 증명

가짜 웹사이트(피싱 사이트)로 사용자를 유인하여 정보를 탈취하려는 시도를 막습니다. HTTPS는 공인된 CA(Certificate Authority, 인증 기관)가 발급한 디지털 인증서를 사용해 "이 서버가 진짜 `google.com`이 맞다"는 것을 보증합니다.

### 2. HTTPS의 암호화 동작 원리 (대칭키 + 비대칭키의 조합)

HTTPS는 성능과 보안을 모두 잡기 위해 **비대칭키(공개키) 암호화**와 **대칭키 암호화** 방식을 혼합하여 사용합니다.

- **대칭키 방식:** 암복호화 속도가 매우 빠르지만, 키를 상대방에게 전달할 때 탈취당할 위험이 있음.
    
- **비대칭키(공개키) 방식:** 공개키로 암호화하고 비밀키(개인키)로만 복호화하므로 매우 안전하지만, 연산 비용이 커서 속도가 느림.
    

#### [SSL/TLS Handshake 핵심 흐름]

1. **신원 확인 및 비대칭키 활용 (안전한 키 교환):**
    
    클라이언트와 서버가 처음 연결될 때, 서버는 CA에서 발급받은 인증서와 **공개키**를 클라이언트에게 넘겨줍니다. 클라이언트는 이 공개키를 이용해 향후 통신에 사용할 대칭키(세션 키)를 암호화하여 서버로 전송합니다. 이 세션 키는 서버의 **비밀키**로만 열어볼 수 있으므로 중간에 탈취될 수 없습니다.
    
2. **대칭키 활용 (빠른 데이터 통신):**
    
    서로 안전하게 공유한 대칭키(세션 키)를 사용해 실제 HTTP 데이터를 빠르게 암호화/복호화하며 통신합니다.
    

### 3. HTTP vs HTTPS 한눈에 비교

|**구분**|**HTTP**|**HTTPS**|
|---|---|---|
|**기본 포트**|`80`|`443`|
|**보안 여부**|암호화 없음 (평문 전송)|SSL/TLS 암호화 적용|
|**인증서 필요 여부**|필요 없음|CA 발급 SSL 인증서 필요|
|**속도/비용**|핸드셰이크 과정이 없어 미세하게 빠름|SSL/TLS 핸드셰이크 연산 비용 발생 (최신 HW에선 차이 미미)|
|**SEO (검색 엔진)**|검색 노출 가산점 없음|Google 등 검색 엔진에서 검색 순위 가산점 부여|

### 4. OAuth에서 HTTPS가 "선택"이 아닌 "필수"인 이유

OAuth 2.0 흐름에서는 사용자의 인증 자격 증명 역할을 하는 **`Authorization Code`**, **`Access Token`**, `Refresh Token`이 네트워크를 통해 이동합니다.

만약 OAuth 인증 과정을 HTTP 환경에서 진행할 경우:

1. `Redirect URI`로 넘어가던 `Authorization Code`가 중간에 탈취될 수 있습니다.
    
2. 발급받은 `Access Token`이 노출되어 공격자가 사용자의 계정 권한을 그대로 탈취(Account Takeover)하게 됩니다.
    

따라서 OAuth 2.0 명세(RFC 6749)에서는 Authorization Server 및 Redirect URI 통신 시 HTTPS 사용을 필수(MUST)로 규정하고 있습니다. (단, 개발용 `localhost` 예외)
