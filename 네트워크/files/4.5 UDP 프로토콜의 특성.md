## 1. UDP 프로토콜의 주요 특성

### 1) 비연결성 (Connectionless)
- **사전 연결 설정 없음:** TCP처럼 통신 시작 전 $3$-Way Handshake 과정을 거치지 않습니다.
- **상태 미유지 (Stateless):** 송신 측과 수신 측 사이에 논리적인 연결 상태를 유지하지 않으므로, 데이터가 서로 독립적인 **데이터그램(Datagram)** 단위로 전송됩니다.
- **상대방 수신 여부 미확인:** 데이터를 보낸 후 잘 도착했는지(ACK) 확인하지 않으며, 전송 성공 여부를 추적하지 않습니다.
    

### 2) 속도 중심 (Low Overhead & High Performance)
- **흐름 제어 / 혼잡 제어 부재:** 수신 측의 버퍼 상태나 네트워크 혼잡 상황을 고려하지 않고 송신자 속도대로 곧바로 전송합니다.
- **재전송 메커니즘 없음:** 손실된 패킷을 재전송하지 않으므로 이에 따른 대기 시간(Latency) 및 처리 지연이 발생하지 않습니다.
- **최소한의 헤더:** 데이터 외에 추가되는 제어 정보가 적어 오버헤드가 극히 낮습니다.
    
## 2. UDP 데이터그램 헤더 구조

UDP 헤더는 고정 8바이트(64비트)의 아주 단순하고 경량화된 구조를 가집니다. (TCP 헤더가 기본 20바이트 이상인 것과 대조적입니다.)

```
 0                   16                  31 bit
+-------------------+-------------------+
|   Source Port     |  Destination Port |  (4 Bytes)
+-------------------+-------------------+
|      Length       |     Checksum      |  (4 Bytes)
+-------------------+-------------------+
|               Payload / Data          |
+---------------------------------------+
```

- **Source Port (16 bit):** 송신 프로세스의 포트 번호 (응답이 필요 없거나 미지정이면 $0$ 가능)
- **Destination Port (16 bit):** 수신 프로세스의 포트 번호
- **Length (16 bit):** UDP 헤더와 데이터를 합친 **전체 데이터그램의 길이** (바이트 단위, 최소값은 헤더 크기인 $8$)
- **Checksum (16 bit):** 데이터 전송 중 헤더 및 데이터의 무결성(변조 여부)을 검사하기 위한 필드 (오류 발견 시 데이터 복구가 아닌 **단순 파기** 처리)

## 3. 실시간 스트리밍, DNS, 게임에서 UDP를 채택하는 이유

### 1) 실시간 스트리밍 (Live Video/Audio Streaming)
- **원인:** 화면과 음성의 실시간성(Low Latency)이 최우선입니다.
- 
- **이유:** 중간에 몇 프레임이 손실되어 영상이 순간적으로 튀더라도, 곧바로 다음 프레임을 보여주는 것이 신뢰성을 지키겠다고 $0.5$초 전 패킷을 재전송받느라 방송 전체가 멈추는(Buffering) 것보다 사용자 경험 측면에서 훨씬 뛰어납니다.
    

### 2) DNS (Domain Name System)
- **원인:** 짧은 단발성 요청과 빠른 응답 처리가 핵심입니다.
    
- **이유:** `[www.example.com](https://www.example.com)`의 IP를 물어보는 질의는 데이터 크기가 매우 작습니다. TCP의 연결 설정($3$-Way Handshake) 및 해제 과정은 단 한 번의 IP 조회보다 배보다 배꼽이 더 큰 오버헤드를 유발합니다.
    
- **손실 대처:** 만약 UDP 패킷이 유실되더라도, 클라이언트 타임아웃 메커니즘을 통해 **애플리케이션 계층에서 단순히 요청을 재시도**하는 것이 훨씬 효율적입니다.
    

### 3) 온라인 게임 (Online Multiplayer Games)
- **원인:** FPS, MOBA, 격투 게임 등에서는 플레이어의 위치나 동작 데이터가 초당 수십 번 이상 갱신됩니다.
    
- **이유:** $0.01$초 전 플레이어의 좌표 패킷이 유실되었을 때, 이를 다시 받기 위해 뒤이어 오는 최신 좌표 패킷들을 대기 상태(Head-of-Line Blocking)로 두면 심각한 렉(Lag)이 발생합니다.
    
- **해결:** 과거 좌표 패킷은 버리고 **가장 최근에 도달한 좌표 패킷으로 캐릭터 상태를 빠르게 업데이트**하는 것이 게임플레이 유지에 훨씬 유리합니다. (필요한 경우 게임 엔진 내부에서 최소한의 커스텀 신뢰성 기법을 UDP 위에 얹어 구현합니다.)
