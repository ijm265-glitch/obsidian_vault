## 1. 인터넷 주소의 전체 구조
-  `https://www.google.com.`이라는 주소가 있다고 할 때 (편의상 맨 뒤에 점이 있지만 생략하고 사용함) 주소는 오른쪽에서 왼쪽 방향으로 작아지는 tree구조임
```
[ Root ]                .  (맨 뒤의 숨겨진 점)
                        │
[ TLD ]              .com / .kr / .org / .net
                        │
[ SLD / Domain ]     google / naver / daum
                        │
[ Subdomain / Host ]  www / mail / blog
```

#### ① 프로토콜 (`https://`)

- 이건 도메인 이름이 아니라, **"어떤 규격(통신 방식)으로 데이터를 주고받을지"** 정하는 규칙입니다. DNS가 IP를 찾을 때는 이 부분을 전혀 신경 쓰지 않습니다.
#### ② Root Domain (최상위 루트: `.`)

- 주소의 맨 오른쪽에 눈에 보이지 않게 숨어있는 점(`.`)입니다.
    
- 전 세계 인터넷 세상 전체를 대표하는 뿌리(Root)입니다.

#### ③ TLD (Top-Level Domain, 1단계 도메인: `.com`, `.kr` 등)

- Root 바로 아래에 있는 **가장 큰 카테고리**입니다.
    
- **국가 코드 TLD:** `.kr`(한국), `.jp`(일본), `.us`(미국) 등
    
- **일반 TLD:** `.com`(상업), `.org`(기관), `.net`(네트워크) 등
    
#### ④ SLD (Second-Level Domain) / Domain Name (2단계 도메인: `google`, `naver` 등)

- 우리가 돈을 주고 구매하는 **조직이나 서비스의 고유 이름**입니다.
    
- `.com`이라는 큰 카테고리 안에 `google`이라는 이름이 들어가는 구조입니다.
    
#### ⑤ Subdomain / Host (3단계 도메인: `www`, `mail` 등)

- 해당 조직 내부에서 **어떤 특정 서버/서비스**를 가리키는지 구분하는 이름입니다.
    
- `[www.google.com](https://www.google.com)`은 웹사이트용 서버, `mail.google.com`은 메일용 서버를 뜻합니다.

## 2. DNS 서버의 4가지 주요 구성 요소

도메인 탐색 과정은 계층 구조로 이루어진 여러 DNS 서버가 협력하여 작동합니다.

- **Local DNS (Recursive Resolver / Cache Server):**
    
    - 사용자의 PC/스마트폰이 가장 먼저 질의를 보내는 DNS 서버입니다. 보통 가입한 ISP(KT, SKT, LGU+)의 DNS 서버이나, public DNS(`8.8.8.8`, `1.1.1.1`)를 쓰기도 합니다.
        
    - 이전 질의 결과를 캐시(Cache)에 저장해 두며, 캐시에 없으면 클라이언트를 대신해 전체 DNS 계층을 돌며 IP를 **재귀적으로 찾아와 주는 책임**을 집니다.
        
- **Root DNS Server:**
    
    - DNS 계층 구조의 최상위에 위치하는 서버입니다.
        
    - 전체 도메인 이름의 최우측 루트(`.`)를 담당하며, `.com`, `.net`, `.kr` 같은 TLD DNS 서버의 위치(IP 주소)를 안내합니다.
        
- **TLD (Top-Level Domain) DNS Server:**
    
    - 최상위 도메인(`.com`, `.org`, `.kr` 등)을 관리하는 서버입니다.
        
    - 해당 TLD 하위에 속한 **Authoritative DNS 서버의 위치**를 안내합니다. (예: `google.com`의 Authoritative DNS가 어디 있는지 알려줌)
        
- **Authoritative (권한 있는) DNS Server:**
    
    - 도메인의 실제 IP 주소 정보를 **최종적으로 소유하고 관리하는 서버**입니다.
        
    - 도메인 구매 사이트(가비아, GoDaddy 등)나 AWS Route 53 등에 등록된 DNS 레코드 정보(A, AAAA, CNAME 등)가 실제로 저장되어 있습니다.
        

## 3. 도메인 네임 변환 메커니즘 (Query 방식)

DNS 질의 과정은 크게 Recursive Query(재귀적 질의)와 **Iterative Query(반복적 질의)** 두 가지 방식으로 나뉩니다.

Plaintext

```
[ Client ] 
   │  ▲
   │1 │ 8 (Recursive Query)
   ▼  │
[ Local DNS ] ──2. Root 질의───► [ Root DNS ]
   ▲        ◄──3. TLD 위치 응답──
   │
   │          ──4. TLD 질의────► [ TLD DNS (.com) ]
   │          ◄──5. Auth 위치 응답─
   │
   │          ──6. Auth 질의───► [ Authoritative DNS ]
   └──────────◄──7. 최종 IP 응답── (Iterative Queries)
```

### 1) Recursive Query (재귀적 질의)

- **주체:** Client $\rightarrow$ Local DNS
    
- **특징:** "완전한 최종 정답(IP 주소)을 가져다줘!"라고 요청하는 방식입니다.
    
- **과정:** 클라이언트는 Local DNS에게 IP를 물어보고, Local DNS가 최종 IP를 찾아다 줄 때까지 얌전히 대기합니다. Local DNS는 클라이언트 대신 전체 탐색을 완수해야 하는 의무를 집니다.
    

### 2) Iterative Query (반복적 질의)

- **주체:** Local DNS $\rightarrow$ Root / TLD / Authoritative DNS
    
- **특징:** "내가 모르면 아는 놈 위치(다음 서버)라도 가르쳐줘!"라고 요청하는 단계적 핑퐁 방식입니다.
    
- **과정:**
    1. **Local DNS $\rightarrow$ Root DNS:** "`[www.example.com](https://www.example.com)` IP 알아?" $\rightarrow$ **Root:** "몰라, 대신 `.com` TLD 서버 IP 알려줄게."
        
    2. **Local DNS $\rightarrow$ TLD DNS:** "`[www.example.com](https://www.example.com)` IP 알아?" $\rightarrow$ **TLD:** "몰라, 대신 `example.com` 관할 Authoritative 서버 IP 알려줄게."
        
    3. **Local DNS $\rightarrow$ Authoritative DNS:** "`[www.example.com](https://www.example.com)` IP 알아?" $\rightarrow$ **Auth:** "응! 최종 IP는 `93.184.216.34`야."
        

## 4. 전체 동작 시나리오 (단계별 흐름)

웹 브라우저 주소창에 `[www.example.com](https://www.example.com)`을 입력했을 때 일어나는 전체 과정입니다.

1. **브라우저 및 OS 캐시 확인:** PC 내부(브라우저 캐시, OS 캐시, `hosts` 파일)에 기존에 접속했던 IP 정보가 남아있는지 확인합니다. 있다면 과정을 바로 종료합니다.
    
2. **Local DNS 캐시 확인:** PC 캐시에 없으면 Local DNS 서버로 **Recursive Query**를 보냅니다. Local DNS 캐시에 정보가 존재하면 즉시 IP를 반환합니다.
    
3. **Root DNS 질의:** Local DNS 캐시에도 없다면, Local DNS는 **Root DNS**에 **Iterative Query**를 보냅니다. Root는 `.com` TLD 서버 IP를 응답합니다.
    
4. **TLD DNS 질의:** Local DNS는 **`.com` TLD DNS**에 질의합니다. TLD는 `example.com`의 **Authoritative DNS** 서버 IP를 응답합니다.
    
5. **Authoritative DNS 질의:** Local DNS는 **Authoritative DNS**에 질의하여 `[www.example.com](https://www.example.com)`에 해당하는 최종 IP 주소를 얻습니다.
    
6. **응답 및 캐싱:** Local DNS는 얻어낸 최종 IP 주소를 클라이언트(PC)에 전달함과 동시에, 설정된 **TTL(Time To Live)** 시간 동안 자신의 **Local DNS Cache**에 저장해 두어 향후 동일 요청 시 신속하게 응답합니다.
