### ① Discover (탐색 - "저 접속했어요!")
- **상황:** ESP32가 Wi-Fi 비밀번호를 맞추고 네트워크에 물리적으로 연결되었지만, 본인의 IP도 모르고 공유기 IP도 모릅니다.
- **외치는 방법:** 목적지 IP를 `255.255.255.255` (전체 브로드캐스트)로 설정하고 네트워크에 냅다 찌릅니다
- **내용:** _"나 방금 접속한 ESP32(MAC 주소: `XX:XX`)인데, 나한테 IP 할당해 줄 DHCP 서버(공유기) 있나요?!"_
### ② Offer (제안 - "이 번호 어때?")
- **상황:** ESP32가 쏜 외침을 공유기의 DHCP 서버 모듈이 받습니다.
- **내용:** 공유기는 자신이 관리하는 장부(`192.168.0.X`)를 확인하고 비어있는 가장 빠른 번호를 하나 골라 제안합니다.
    - _"어 오케이! 너한테 `192.168.0.2`라는 IP를 빌려줄 수 있는데, 이거 쓸래?"_
        
### ③ Request (요청 - "그 번호로 정할게요!")
- **상황:** ESP32가 공유기의 제안을 받아들입니다.
- **내용:** 다시 브로드캐스트로 승인 요청을 보냅니다. (네트워크에 혹시 다른 DHCP 서버가 더 있을 수도 있어서 전체에 알립니다.)
    - _"좋습니다! 공유기님, 저 `192.168.0.2`번 IP 쓰겠다고 요청합니다!"_

### ④ ACK (확인 - "최종 등록 완료!")
- **상황:** 공유기가 요청을 최종 승인하고 임대 장부에 기록합니다.
- **내용:** _"오케이, `192.168.0.2` 등록 완료! 서브넷 마스크는 `255.255.255.0`이고, 밖으로 나가는 문(기본 게이트웨이)은 내 주소인 `192.168.0.1`이야. 잘 써라!"_

### 3. ESP32가 DHCP Request를 쏠 때의 실제 포장 과정 (L4~L1)
ESP32가 공유기에게 IP를 달라고 쏠 때 내부에서 일어나는 실제 포장 단계를 열어보면 다음과 같습니다:

```
[ Application ] ──► DHCP 프로토콜 메시지 생성 ("IP 주세요!")
        │
        ▼
[ L4 (UDP) ]    ──► 출발지 포트: 68 / 목적지 포트: 67 (DHCP 전용 포트)
        │
        ▼
[ L3 (IP) ]     ──► 출발지 IP: 0.0.0.0 (내 IP 없음) 
        │           목적지 IP: 255.255.255.255 (로컬 브로드캐스트)
        │
        ▼
[ L2 (Ethernet) ] ──► 출발지 MAC: ESP32의 실물 MAC 주소 (예: 24:0A:C4:XX:XX:XX)
        │            목적지 MAC: FF:FF:FF:FF:FF:FF (브로드캐스트 MAC)
        ▼
[ L1 (Physical) ] ──► Wi-Fi RF 무선 신호(2.4GHz)로 공기 중에 발송!
```

1. **4계층 (L4):** 신뢰성보다는 빠르게 쏘는 게 중요한 브로드캐스트이므로 **UDP**를 사용하며, DHCP 전용 포트인 **`67`번**을 목적지로 적습니다.
    
2. **3계층 (L3):** 내 IP가 없으므로 출발지는 **`0.0.0.0`**, 목적지는 방금 배운 `255.255.255.255`를 적습니다.
    
3. **2계층 (L2):** 칩 제조 단계에서 랜칩에 박혀 나온 **ESP32의 고유 MAC 주소**를 출발지에 적고, 목적지 MAC은 `FF:FF:FF:FF:FF:FF`로 포장합니다.
    
4. **1계층 (L1):** 랜선 대신 **Wi-Fi 안테나**를 통해 전파 신호로 쏘아 보냅니다.
