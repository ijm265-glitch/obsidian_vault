앞서 요약했던 3번 항목("언제 무엇을 써야 할까?")은 **실무 아키텍처 설계에서 가장 중요한 핵심 기준**입니다.

문법을 아는 것과 *"실제 프로젝트에서 둘 중 무엇을 골라야 하는가?"*는 별개의 문제인데요, 이 6가지 기준을 하나씩 구체적인 예시와 함께 아주 쉽고 깊게 풀어드리겠습니다.

## Part 1. 추상 클래스(Abstract Class)를 선택해야 할 때

> **핵심 키워드:** 정체성(Is-A), 상태 공유, 하위 호환성

### 1. 상속받을 클래스들이 밀접하게 연관되어 있을 때 (개념적 연관성)

- **의미:** *"우리는 본질적으로 같은 뿌리에서 나왔다"*라는 명확한 부모-자식 관계일 때 사용합니다.
- **실무 비유:**
    - `Dog`, `Cat`, `Lion` $\rightarrow$ 모두 `Animal`이라는 명확한 본질을 공유합니다.
    - `PdfExporter`, `ExcelExporter` $\rightarrow$ 모두 `DataExporter`라는 본질을 공유합니다.
- **왜 추상 클래스인가?**    
    단순히 기능만 공유하는 게 아니라, "너희는 본질적으로 이 종류의 객체다"라는 강한 결합을 맺어주어 코드의 개념적 구조를 깔끔하게 잡아주기 때문입니다.

### 2. 클래스 간에 공통 상태(변수/필드)나 공통 코드를 공유하고 싶을 때

- **의미:** 자식 클래스들이 똑같이 가지는 '데이터(필드)'와 '이미 완성된 로직'이 많을 때 쓰면 중복 코드를 획기적으로 줄일 수 있습니다.
- **구체적 예시:**
    ```cs
    public abstract class Enemy
    {
        // 1. 공통 상태 (인터페이스에서는 선언 불가능한 순수 필드)
        protected int hp = 100; 
        protected int attackPower = 10;
    
        // 2. 공통 코드 (자식들이 토씨 하나 안 틀리고 똑같이 쓸 로직)
        public void TakeDamage(int damage)
        {
            hp -= damage;
            Console.WriteLine($"피해를 입었습니다. 남은 체력: {hp}");
            if (hp <= 0) Die();
        }
    
        public abstract void Die(); // 죽는 연출만 적에 따라 다르게!
    }
    ```
    
    `Goblin`, `Orc`, `Dragon` 등 100개의 적이 존재해도 피격 로직(`TakeDamage`)을 일일이 새로 짤 필요 없이 **추상 클래스에 한 번만 작성**하면 끝납니다.
    

### 3. 나중에 공통 기능을 추가하여 하위 클래스에 일괄 반영하고 싶을 때

- **의미:** 프로젝트가 커지면서 부모 쪽에 새로운 기능을 슬쩍 추가해도, 자식 클래스들의 기존 코드가 깨지지 않고 **자동으로 새 기능을 물려받게** 만들 수 있습니다.
- **상황 비유:**
    어느 날 기획자가 *"모든 적 캐릭터에 '로그 남기기' 기능을 추가해 주세요!"*라고 요구합니다.
    - **추상 클래스라면?** 부모 클래스에 `public void LogStatus() { ... }` 라는 완성된 메서드 하나만 툭 넣어주면 수십 개의 자식 클래스에 **즉시 일괄 반영**됩니다.
    - **인터페이스라면?** 인터페이스에 새 메서드를 선언하는 순간, 그걸 구현하던 수십 개의 자식 클래스에서 컴파일 에러가 터지며 일일이 수정해 줘야 할 수 있습니다. (※ C# 8.0의 기본 구현 기능이 생겼지만, 여전히 상태 값을 다루는 확장엔 추상 클래스가 훨씬 유리합니다.)
        

## Part 2. 인터페이스(Interface)를 선택해야 할 때

> **핵심 키워드:** 기능(Can-Do), 조합성, 느슨한 결합(DI/Mocking)

### 1. 상속 관계가 서로 다른 다양한 클래스에 동일한 기능을 부여하고 싶을 때

- **의미:** *"너희 둘이 무슨 관계인지는 관심 없고, 둘 다 이 기능(버튼)을 누를 수만 있으면 돼!"*라는 상황입니다.
- **구체적 예시:**
    - `Bird`(동물)와 `Drone`(기계)은 뿌리(부모)가 완전히 다릅니다.
    - 하지만 둘 다 하늘을 나는 기능(`IFlyable`)이 필요합니다.
    - 이때 `IFlyable` 인터페이스를 붙여주면, 전혀 상관없는 두 객체를 "날 수 있는 것들"이라는 하나의 묶음으로 처리할 수 있습니다.
    
    ```cs
    List<IFlyable> flyables = new List<IFlyable>();
    flyables.Add(new Bird());
    flyables.Add(new Drone());
    
    foreach (var item in flyables) item.Fly(); // 완벽하게 동작!
    ```
    

### 2. 다중 상속 형태의 기능 조합이 필요할 때

- **의미:** C#은 클래스의 다중 상속(부모 둘 이상)을 금지합니다. 단 하나의 클래스만 상속받을 수 있죠. 하지만 인터페이스는 **원하는 만큼 조립해서 붙일 수 있습니다.**
- **게임 캐릭터 예시:**
    - 레고 블록처럼 기능을 조합할 때 인터페이스가 진가를 발휘합니다.
    
    ```cs
    // 필요에 따라 마음대로 기능을 '조합'
    public class Player : IAttackable, IMovable, IHealable, ISavable
    {
        // 4가지 인터페이스의 규칙을 모두 구현
    }
    ```
    
    만약 추상 클래스만 쓴다면 `AttackerMoverHealerSaver` 같은 괴물 부모 클래스를 만들어야 했을 것입니다.
    

### 3. 의존성 주입(DI)이나 단위 테스트(Mocking)를 위해 결합도를 낮추고 싶을 때

- **의미:** **C# 현대 프로그래밍(웹, 서버, 앱)의 가장 핵심이 되는 이유**입니다. 객체끼리 너무 끈적하게 결합되어 있으면 유연성이 떨어지고 테스트도 불가능해집니다.
    
- **실무 예시 (결제 시스템):**
    - **나쁜 예 (강한 결합):**
        ```cs
        public class OrderService
        {
            // 진짜 KakaoPay 클래스에 직접 의존함
            private KakaoPay payment = new KakaoPay(); 
        }
        ```
        
        이렇게 짜면 나중에 NaverPay로 바꿀 때 `OrderService` 코드를 통째로 고쳐야 하고, 테스트할 때마다 진짜 카카오페이 서버로 실제 결제 요청이 날아갑니다!
        
    - **좋은 예 (인터페이스를 통한 느슨한 결합):**

        ```cs
        public class OrderService
        {
            private IPaymentProcessor _payment;
        
            // 인터페이스에만 의존 (외부에서 주입받음 = 의존성 주입)
            public OrderService(IPaymentProcessor payment) 
            {
                _payment = payment;
            }
        }
        ```
        
        - **실제 운영 시:** `new OrderService(new KakaoPay())` 전달
        - **테스트 진행 시:** 실제 돈이 안 나가는 가짜 `new OrderService(new MockPay())` 전달
            이처럼 **인터페이스가 중간에서 '가짜/진짜 부품을 언제든 교체할 수 있는 소켓' 역할**을 해줍니다.
            

## 💡 최종 정리 요약

|**어떤 상황인가요?**|**추천 선택**|**이유**|
|---|---|---|
|객체들의 **뿌리(개념)**가 같고, **공통 변수나 구현된 코드**를 나눠 갖고 싶다|**추상 클래스**|코드 재사용성과 부모-자식 관계가 명확함|
|전혀 다른 객체들에게 **특정 기능(행동)**만 다발로 쥐여주고 싶다|**인터페이스**|다중 상속이 가능하며 부품처럼 조립 가능함|
|**부품 교체, 단위 테스트, 의존성 주입(DI)**이 용이한 구조를 만들고 싶다|**인터페이스**|객체 간의 결합도를 완벽히 떨어뜨려 줌|
